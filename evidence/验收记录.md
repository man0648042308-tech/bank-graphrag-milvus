## 真实失败与修复

### F01：Windows Docker 引擎未运行

- 现象：Docker API 命名管道不存在，本机数据库端口未监听。
- 根因：Docker Desktop 引擎未启动。
- 修复：启动 Docker Desktop 后先用 `docker info` 验证，再启动隔离容器。
- 回归：Neo4j 和 Milvus 均 healthy。

### F02：Milvus 写入后立即检索断言失败

- 现象：插入5条后第一次即时混合检索没有稳定返回 P001/P005。
- 证据：测试抛出 `AssertionError`；稍后查询返回 P005、P001、P002。
- 根因：写入与搜索可见性的时序边界。
- 修复：写入后显式 `client.flush(collection_name)`。
- 回归：重建 collection 后 `MILVUS_INTEGRATION_PASS`，完整27项测试通过。

### F03：虚拟机可启动但自动 SSH 认证不可用

- 现象：VMware DHCP 地址变为 `192.168.220.128`，22端口可达，但无可用非交互认证。
- 决策：不记录或反复尝试密码，不修改 VMware 磁盘和配置；改用 Windows Docker 隔离容器完成真实集成。
- 残余：未在虚拟机内重复验收；本次提交的真实运行环境是 Windows Docker Desktop。

### F04：两份 Compose 使用了相同默认项目名

- 现象：重跑 Neo4j 启动脚本时，Docker 把 Milvus 容器识别为 orphan，并出现网络冲突。
- 根因：两份 Compose 位于同一目录，Docker 自动推导出相同项目名；服务名不同不足以隔离项目生命周期。
- 修复：分别声明顶层项目名 `day3536-neo4j-stack` 和 `day3536-milvus-stack`；只重建四个容器外壳，保留全部 `day3536_*` 命名卷。
- 回归：两套脚本可重复运行，互不停止或移除对方服务；Neo4j 与 Milvus 集成测试再次通过。

### F05：Neo4j 插件入口重复下载 GDS 并超时

- 现象：容器重建时 `NEO4J_PLUGINS` 再次从插件站下载 GDS，5分钟后文件仍不完整，健康检查超时。
- 根因：自动插件入口每次启动都会重新获取大文件，容器内下载链路当时速度异常；原插件文件还被不完整下载覆盖。
- 修复：启动脚本先检查插件命名卷中文件大小；缺失或小于60MB时由 Windows `curl.exe` 下载并校验，再复制到命名卷。Compose 自动插件列表只保留镜像内置的 APOC。
- 回归：GDS 2.13.12 从持久卷加载，Neo4j 约几十秒达到 healthy；`RETURN gds.version()` 和全部图算法再次通过。
